# Independent review v2 (whole-network expansion)

Reviewer: an AI agent (Claude), separate session from the builders. Code-reading plus data probes plus the existing test suite. NOT a human, field or device review. Nothing in the repo except this file was modified. Importer not run. No browser/Playwright run, so every browser-level and visual statement is "code-read" or "unverified".

## 1. Scope

Change set `a6a17a3..HEAD` (v2). Items reviewed: (1) new control model, (2) level catalogue and menu, (3) v2 loading and world-version separation, (4) road tile streaming and `onlyTile`, (5) traffic/pedestrian/autopilot fixes, (6) route matching and surface scoring, (7) importer `limitGrades` and elevated-building intrusion rule, (8) storefront/structure integration and disposal, (9) credits licensing text.

## 3. Findings

### Major

**M1. In-game credits state the wrong licence for buildings and base layers.**
`src/ui/screens.ts` credits(), the network-only paragraph (about line 293): "Places, buildings and base layers: CDLA-Permissive-2.0. Transportation layer (c) OpenStreetMap contributors, ODbL 1.0."
`DATA_SOURCES.md` section v2.1 (lines 179-191) and `sources-manifest.json` `licence_summary` say the opposite: buildings are ODbL-1.0 (OSM, Microsoft ML buildings) or Google Open Buildings with no licence value; base is ODbL-1.0; only Places is CDLA-Permissive-2.0 (plus Apache-2.0 Foursquare, CC0 AllThePlaces). The doc itself says the "all CDLA" assumption is wrong.
Failure scenario: shipped attribution misstates the licence of about 80k footprints and omits TomTom/Microsoft/Google attribution and the ODbL share-alike notice. The generic v1 paragraph that follows is also printed on the v2 build ("dated OSM extracts bundled with this build ... storefront inventory is incomplete"), which contradicts the v2 text.
Fix: use the attribution block from DATA_SOURCES.md line 189 verbatim (ODbL for roads/buildings/metro/base, CDLA/Apache/CC0 for listings, source credits for TomTom/Microsoft/Google), add the ODbL offer/notice, and render the v1 paragraph only when `!isNetwork()`. Legal sign-off on the Google building licence remains open (DATA_SOURCES says so).

**M2. Storefronts of omitted (carriageway-intruding) buildings are still rendered, with no collision.**
`src/app/app.ts:397` removes buildings with `intrudesCarriageway` from the chunk passed to `view.addChunk`; `src/app/view.ts:111-113` then builds storefronts from the same chunk object; `src/art/storefronts.ts:363-380` looks up `byBuilding.get(sf.buildingId)`, gets `undefined`, silently falls back to `H = 9`, and still emits `store-body`, boards and signs.
Measured on the shipped data: 2046 of 19507 storefront records (10.5 %) reference a building that is flagged `intrudesCarriageway` (example `c_-10_-8.json` `sf_9d120613a3` -> `b_48b48bd8e0`). The building and its collider are dropped (D12 road precedence), but the shop box, board and sign stay: floating or road-overlapping boxes that the car drives through. Whether the box visibly overlaps the carriageway depends on where the facade line sits: unverified visually.
Fix: in `buildStorefronts` (or in `addChunk`) skip storefronts whose `buildingId` is flagged, or have the importer drop/flag them (`storefronts` entries with `buildingId` in the intruding set). Add a validator rule: no storefront may reference an `intrudesCarriageway` building.

**M3. Level bands do not match the approved plan; Level 4 is not "through real interchange roads".**
`src/missions/levels.ts:55-62` vs `EXPANSION_PLAN.md` section 5 (lines 68-72): L3 is 3.5-6 km (plan 5-10), L5 is 7.5-10 km (plan 15-25 km; the header comment at levels.ts:7-10 still says 12-30 km and 4-14 km for L4), L2 1.5-4 (plan 2-4), L1 0.4-1.5 (plan 0.5-1.5). L4 and L5 differ only by length: the predicate is `!sharesLine`, where `sharesLine` is derived from the nearest station of each delivery; no interchange (Ameerpet, MGBS, Parade Ground) is required or checked. L4 "cross-line" can therefore be a pair that merely sits near different stations.
There is an in-code remark that L5 is "kept to a phone-session length", but the plan, the header comment and the UI blurb ("Long cross-network contracts") were not updated, and I found no recorded decision to deviate.
Fix: either record the deviation in the plan and fix the header comment, or restore the bands (and add an interchange predicate: route passes within X m of an interchange station node). Deadlines themselves do follow `deadlineFor(r.lengthM, r.turns, 1, margin)` (levels.ts:80), margin 1.8 for L1 and 1.6 otherwise, matching `catalog.ts:62`; flight budgets are fixed by level (25, 20 for L3 MT06, 30 for L5), not derived from `deadlineFor`.

### Minor

**m1. Catalogue ordering uses `localeCompare` (levels.ts:41, 53, plus catalog.ts:77).**
Mission ids and the `(i*7 + level*13) % sorted.length` start index depend on the sort order. `localeCompare` is ICU/locale dependent, so two devices with different locales can produce different catalogues, so saved `progress.completed` ids and checkpoint `missionId` can silently stop matching. Ids are ASCII, so it is unlikely but not impossible. Fix: compare with `a < b ? -1 : a > b ? 1 : 0`. Mission ids also embed a running index `n`, so any change in candidate order renames missions; use a stable key (pickup id + stop id) instead.

**m2. Checkpoint slot and progress are not partitioned by world; a world switch deletes the save.**
`src/persistence/store.ts` uses one `checkpoint` slot; `app.ts:362-367` `continueSaved` calls `reject()` -> `clearCheckpoint()` when the mission id is not in the current catalogue. A player with a v1 save who first loads v2 (or opens `?v1` after a v2 save) loses the checkpoint, with a message. `WORLD_VERSION_KEY` (`session.ts:12-14`) does separate best-score keys and checkpoint compatibility, but `progress.completed` is shared (ids are disjoint today, so no clash). Fix: key `checkpoint`/`progress` by `WORLD_VERSION_KEY`, or at least do not clear on a world mismatch.

**m3. Level unlock bypass in production builds.**
`src/ui/screens.ts` uses `a.debug`, which is `new URLSearchParams(location.search).has('debug')` (`app.ts:58`), not a build flag. Appending `?debug` to any production URL unlocks all levels (and shows debug HUD). Records are still blocked only when the autopilot is used (`debugUsed`). Fix: gate on `import.meta.env.DEV` or similar if "debug builds" is the intent.

**m4. Road tile build context is incomplete for edges that extend beyond the tile (code-read, visual unverified).**
`src/app/view.ts:268-285` indexes an edge into every tile its bbox overlaps (+40 m) but `buildRoadTile` (view.ts:287-297) passes only those roads and their nodes. `roads.ts` emits an edge's whole geometry into the tile of its midpoint (`tileFor(mid)`, roads.ts:323), yet computes `joinPair` frames (roads.ts, `ends` map), `cont()` (free-end test, uses `infos.has(otherEdge)`), junction radius (`nodeInfo` max width) and `raised` only from the roads present. For an edge whose far end node is more than 40 m outside the tile, the neighbouring edges at that node are absent, so in this build the end counts as a free end: an end face and parapet end faces are drawn on a continuous deck, the shared frame is not applied (seam/gap against the neighbour built in the other tile), and kerb/marking cuts use a smaller junction radius. Only affects long edges; cosmetic. Fix: in `initRoadStream`, also add to each tile every road incident to a node of an already-included road (one hop). A unit test that compares the union of streamed tiles with a full build (vertex count per edge) would catch this.

**m5. A very long edge can be un-drawn under the car on "low" quality.**
`updateRoadTiles` (view.ts:307-325) loads a tile only when the tile centre is within `R + 0.71*480` of the camera, `R = 0.9*camera.far` (low: 650 -> R 585, so about 926 m), but an edge is emitted only into its midpoint's tile. Edge `r_39952830446_0` (1744 m secondary): its far end is 963 m from the midpoint-tile centre, which is outside 926 m, so at the far end of that edge on low quality (the mobile default) the road under the car is not built. Only that one edge in v2 qualifies today (computed over all edges of 500 m or more). Fix: also load the tiles containing the car's current road edge midpoint, or split edges longer than about 500 m in the importer, or emit per-segment into the segment's tile.

**m6. Disposal of road tiles leaks GPU instance buffers; first-view pop-in.**
`disposeRoadTile` (view.ts:299-306) calls `geometry.dispose()` for each mesh child, and the shared-geometry list. Shared materials are correctly not disposed. But the `InstancedMesh` children (`bridge-piers`, `bridge-pier-caps`, roads.ts:560-595) are never `mesh.dispose()`d, which is what frees `instanceMatrix` in three (geometry.dispose does not). Two small buffers leak per tile with piers; bounded by tile churn but unbounded over a long session. Fix: in the traverse, `if ((o as THREE.InstancedMesh).isInstancedMesh) (o as THREE.InstancedMesh).dispose()`. Also `registerCull` (`art/cull.ts`) keeps one entry per built tile/chunk group until GC (WeakRef), so it grows with churn (harmless but loops every frame). Separately, `updateRoadTiles` is only called from `render()`, nearest tile first (budget 2), others 1 per frame, so a mission start or recovery teleport shows roughly 15-25 frames of partially drawn roads (perf and visual: unverified). Fix: pre-warm tiles around the start during the "Warming up graphics" step.

**m7. Elevated-building intrusion rule treats tunnels as at-grade.**
`scripts/import-world-v2.mjs:582` and `scripts/validate-world.mjs:841` skip only samples with `elev > 2.5`; tunnel samples have negative elevation (18 tunnels, e.g. `r_11197947038_0` 0,-3,-3,-0.79,0), so every building above a tunnel is flagged `intrudesCarriageway` and removed from render and collision. Fix: also `continue` for `r.tunnel` / negative `sm.elev`. The validator re-implements the same rule, so it cannot catch this (same-source check); add an independent assertion for tunnel roads.

**m8. `limitGrades` can lower flyovers below their crossing clearance; convergence cap is silent (unverified).**
`scripts/lib/elevation.mjs` (new `limitGrades`, loop `it < 200`). It only moves values toward zero, shares node values by smallest magnitude (sign-consistent since `repairNodeElevations` first equalises nodes), and sets `elevationM = max(pointElevM)` like `computeElevations`, so node consistency, sign handling and the elevationM convention are fine by reading. Two risks: (a) a bridge/flyover whose own ramp is steeper than 10 % (e.g. 6.5 m over a short free end) gets its deck lowered along the ramp, and also at the crossing if the crossing is within the ramp; I did not check minimum clearance (about 5 m plus slab) above at-grade roads that cross under a lowered deck; add a validator rule for deck-to-road clearance at crossings. (b) If 200 iterations pass without convergence the function returns normally; the caller only stores the stats. Fix: assert `iterations < 200` or fail the import.

**m9. Route matching can report "on route" from the wrong level (code-read).**
`src/missions/session.ts:380-392`: `surface(..., { onlyRoadId, maxY: p.y + 0.3 })` excludes surfaces above the car but not the route road if it lies below the car (a flyover running over the route road, or the car on a deck while the route continues at grade under it). The deck is not on the route, so the fallback is entered, the at-grade road under the car matches (`dist <= halfWidth + slack`), and `d` is replaced by the route edge: progress and "not off route" while on the wrong level. Fix: when grounded, additionally require `Math.abs(hit.elevation - (p.y - 0.3)) < 1.5` (or use `preferLevel`). The widened slack (4.5 m and margin 5 when `d.wrongWay`) is only used when the car is classified wrong-way on its current edge, so it does not let a car on the oncoming carriageway match; acceptable.

**m10. Surface score change makes the stickiness penalties much stronger (`src/world/roadIndex.ts:126`).**
The distance term is now 0-2 for points on a carriageway (previously metres), but the penalties kept their size: +30 level, +0.5/+2.0 not-preferred road, +0.5 per metre below the car, +8 heading. A non-preferred, unconnected road now needs to be roughly a full half-width better on normalised distance to win, so the car stays attached to the previously preferred road until it leaves that road's width plus margin (0.5 m). That helps forks (the intent) but delays switching at crossings with parallel roads. No failing case found; unverified. Fix: confirm with a fork/crossing fixture test; if needed scale penalties to the new range.

**m11. Controls: minor behaviours to confirm (all code-read).**
- `player.ts:359-362`: reverse engages once ▼ has been held 18 ticks with `|speed| < 0.3`. Braking to a stop and simply keeping ▼ down turns into reverse 18 ticks later; this is the specified behaviour ("▼ held while stopped"), but a player who holds ▼ to wait at a stop will roll backwards (up to 3 m/s). During a delivery hold (`holdStop`) reverse is suppressed correctly (branch order, line 371), so the hold cannot be broken by ▼.
- `backHeldStopped` only resets when ▼ is released; ticks spent below 0.3 m/s accumulate across a stop-start with ▼ continuously held (for example braking to a stop at 0.2 m/s then briefly above 0.3 m/s). Harmless, but not "continuous 18 ticks".
- After a modal or pause, `clearAll()` clears pressed keys; a key still physically held is ignored until re-pressed because `keyDown` drops `e.repeat` events (`input.ts:40`). Not a stuck state, just a requirement to re-press.
- Reverse never gets stuck: `reverseEngaged` is cleared whenever ▼ is not held (`player.ts:361`), and a launch resets the counter (`player.ts:279`).
- Hold cancel: `session.ts:175` cancels on `input.accel` and re-arms only after leaving the stop polygon or exceeding 2 m/s (`:240`), so a cancelled hold at the exact stop shows "Stop here to deliver" until the player drives away and back; intended, but worth a tutorial line.
- Landing confirm: with no input the car keeps landing speed during `LANDING_CONFIRM` and then decays at 4 m/s^2 (about 30 m from 15 m/s); a stuck state is not reachable (confirm times out in `resolveSurface`). Touch/keyboard parity holds: ▲/▼ pointer sets and key sets feed the same `sample()`, `pointercancel`, `lostpointercapture`, `blur`, `pagehide`, `visibilitychange` all release. One parity gap: touch fly uses `pointerleave` only to remove the CSS class, it does not set anything held, so there is nothing to stick.

### Notes

- **Determinism (item 5):** no `Math.random` in sim paths. `Math.random` appears only in the camera shake (`view.ts:243`), the run id (`session.ts:80`) and the seed for a "new seed" retry (`app.ts:310`, recorded in the session). Pedestrian changes consume `rng` in the same order whether or not the new filters reject a candidate (rejected candidates `continue` before their draws; the cross-side probe uses no rng). `this.peds` is reassigned each update after removing `gone` peds; no external holder of the old array found in `src`. Autopilot level checks (`|dy| > 2.5`) and traffic player-following (`|player.y - a.y| < 2.5`) use consistent thresholds.
- **Pedestrians:** spawn filters (`traffic.ts:146`) work off `footpath === false`, bridge/tunnel, max elevation > 0.3, link classes. `onOtherCarriageway` uses `surface(..., margin 0.3)` and a 1.5 m level window, so footpaths bounce at every side-road mouth (turn back) and are removed only if still on a carriageway after reversing. Performance: one extra `surface()` per walking ped per tick; acceptable.
- **v2 loader:** v2 first, v1 fallback on any non-Abort error (including a missing or HTML-fallback manifest), `?v1` forces v1 (`app.ts:128-134`). Note that the fallback covers only the manifest; if `core.json` of v2 fails after a good manifest the app goes to the error screen instead of falling back. `setWorldVersionKey` runs before any checkpoint is read and yields `hyd-uppal-tarnaka@v1` for v1, so existing v1 saves keep their key.
- **Structures:** `structureObstacles` registers columns, stair flights and lift towers only; skywalk/footbridge decks themselves have no collider or overhead band, so a flying car can pass through a deck (visual only; not verified in play). Registration is guarded by `core.structures.length` and uses the same layout function as the renderer.
- **Storefront atlas disposal:** `removeChunk` (view.ts:118-127) does call `disposeStorefronts` on the `storefronts` child, which frees the sign texture, sign material and geometries, then the generic traverse disposes remaining geometries (double dispose of already-disposed geometries is harmless). One residual risk: `buildStorefronts` finishes painting asynchronously (`userData.pending`, Telugu font); if the chunk is removed before that promise resolves, `paint()` marks the already-disposed texture `needsUpdate`, so it would re-upload and leak one atlas. Unverified, low likelihood.
- **Deadlines:** deadline basis string in `levels.ts` says "verified by reference agent (ground only)"; the L1-L2 calibration is stated in the commit log, but L3-L5 calibration was not run by me (skipped suites).
- Not verified: any rendering, frame time, touch behaviour on a device, the importer output beyond the cross-counts above, `sources-manifest.json` completeness beyond the licence summary text.
